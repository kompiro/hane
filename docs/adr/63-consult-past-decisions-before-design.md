# ADR-63: 設計着手前の「過去決定（特に却下）の確認」を skill 手続きに埋め込む

- **日付**: 2026-07-09
- **ステータス**: 決定済み
- **Issue**: [#63](https://github.com/kompiro/hane/issues/63)
- **関連**: [ADR-8](8-issue-based-doc-numbering.md)（説明的なファイル名 = 検索の入口）, [ADR-55](55-skill-deprecation-convention.md)（frontmatter を唯一の真実にする発想）, `design-doc` skill, `start-dev` skill, `design-doc/ADR-TEMPLATE.md`, 典拠記事「仕様蓄積効果」 <https://fukurou.kompiro.dev/ja/spec-accumulation-effect/>

## 背景

「仕様蓄積効果（spec accumulation effect）」の実験は、過去の設計判断（ADR）が
コーディングエージェントの質・安全性をどれだけ改善するかを測定した。従来の研究が
効果を捉えられなかったのは観察単位が不適切だったためで、「**過去の決定に衝突する
新規依頼**」を単位に変えて初めて差が可視化された。主な発見:

1. **確認を手続きに埋め込むのが最大レバー**。「設計前に必ず過去決定を確認する」
   という単一ルールが、却下決定への到達を 0/3 → 3/3 に反転させた。記録そのもの
   より数倍効いた。
2. **文書化は「却下決定」に集中すべき**。採用済みの決定は生き残る実装から再構成
   できるが、却下（やらないと決めたこと）は実装に痕跡が残らず、記録しないと失われる。
3. **最小限の記録で十分**。結論 + ステータスだけでも効果が出る。厚みより取り出す
   仕組みが本質。
4. **説明的なファイル名が検索の決め手**。重い知識グラフは読まれず、ファイル名と
   本文の語彙が検索を決める。索引に投資するなら軽い一覧で足りる。

hane は skill 群として設計/計画のワークフローを提供している。karasu ではこの確認を
`.claude/rules/` にファイル化したが、hane のネイティブな反映先は **skill の手続き
そのもの**である。反映前の状態では、`design-doc` に「`docs/adr/` を遡って探査」の
記述はあったものの必須の衝突確認として弱く、`start-dev` の計画ステップには明示的な
確認が無かった。

## 決定

上記の学びを hane の skill 手続きに埋め込む。

- **`start-dev` の計画ステップに「過去決定の衝突確認」を必須ステップとして追加**する
  （`docs/adr/` 採用 repo のみ）。計画を書く前に、依頼テーマの語彙で `docs/adr/` を
  grep し、とりわけ**却下決定**との衝突を探し、結果を計画に織り込む。
- **`design-doc` の既存の「過去ドキュメント確認」ステップを、却下決定との衝突を
  明示的に狙う必須確認へ強化**する。
- **`ADR-TEMPLATE` を却下決定ファーストに更新**する。「## 却下した案」の
  「有用な場合のみ」というヘッジを外して最優先で埋める節にし、独立した却下 ADR
  （`ステータス: 却下`）の運用、最小記録で始めてよいこと、slug が検索の入口である
  ことを規約メモに明記する。

## 理由

- 実験が最大の効果を示したのは「確認の手続き化」であり、hane で確認が起きる場所は
  skill の手順そのもの。ここに必須ステップとして書くのが、最小の変更で最大の効果を
  得る反映方法。
- 却下決定は実装から復元できない唯一の情報であり、かつ「衝突する新規依頼」で最初に
  効くのも却下記録。テンプレートの重心を却下側へ寄せるのは、測定された価値の所在に
  一致する。
- 最小記録で可と明記するのは、記録を先延ばしさせないため。厚さを求めると記録が
  後回しになり、確認手続きに供給される在庫が痩せる。
- slug を検索の入口と位置づけるのは、hane が既に軽量採番（ADR-8）で重い索引を持た
  ない方針と整合し、実験結果（重いグラフは読まれない）とも一致するため。

## 却下した案

- **karasu と同じく host repo の `.claude/rules/` に確認ルールを書かせる** — 却下。
  hane はプラグインであり、host の `.claude/rules/` を前提にすると、ルール未整備の
  repo で確認が働かない。skill 手続きに埋め込めば、どの host でも確認が起きる。
  （`init` skill での rules scaffold は将来の別 Issue として残す余地はある。）
- **ADR frontmatter に `status: not_adopted` の controlled vocabulary を導入して
  バリデータで強制する** — 却下（今回は）。hane の ADR-TEMPLATE は素の Markdown で
  あり（ADR-55 の方針）、frontmatter スキーマは host 側の運用に委ねている。まずは
  手続きとテンプレート文言で反映し、機械強制は host repo（karasu 等）の裁量に残す。
- **確認の弱い記述のまま `design-doc` だけ微修正して済ませる** — 却下。最大レバーの
  ステップが必須と読めなければ実行されない。`start-dev` にも必須ステップとして
  明示し、両方の設計入口をカバーする。
